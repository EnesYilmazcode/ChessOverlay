### Two things from those worth not re-learning

**Issue #4 was factually wrong.** Its `truth` column was the standard *starting position*,
diffed against a board that is a checkmate. Diff the reader's correct output for
`testdata/5.png` against `chess.Board()` and you get exactly its "33 of 64". Every other
number in it reproduced. `main` read that fixture 64/64 correctly the whole time. Written
up in a [comment on the issue](https://github.com/EnesYilmazcode/ChessOverlay/issues/4#issuecomment-5493710257).
The method lesson: ground truth in a pixel-reading bug report has to come from the
picture, not from what the position ought to be.

**Issue #3's suggested fix was wrong too.** It proposed `Image.point()` then
`resize((8,8), Image.BOX)`. An 8-bit BOX average returns `round(k*255/324)`, and `255/324`
is under one unit per pixel, so two different counts collapse onto the same byte. Found 35
divergences on crafted squares, every one turning a W into a tie, and a tie scores B. None
fire on a natural board, which is what made it dangerous. There is a comment above
`PIXEL_TAG` in `watcher.py` so nobody re-derives it.

**Staleness was measuring the wrong thing** (from #7). It asked "did the window change
size". Over 152 learn-size and read-size pairs, a set learned at >= 320px reads every board
from 200 to 1600 with no loss against the bundled sheet, in either direction. What costs is
learning *below* 320 and then growing: 240px gives up 3.0 points, 200px gives up 14.4, and
it is the only case in the study that ever named a **wrong piece** rather than `?`. So
`stale()` now asks whether the templates in hand are worse than the sheet, with the floor at
`MIN_LEARN_PX = NORM * 8`. Not a tuned constant: under it a square held fewer screen pixels
than the 40x40 grid its mask is compared on.

### #6 One unreadable square disables the entire check pass -- DO THIS FIRST

Nothing written yet. The workflow was killed during its baseline measurement.

This got more urgent when #12 merged: the margin check deliberately produces more `?`
(unknown squares went 311 -> 503 across the piecetest stress set), so today's behaviour
throws away a larger fraction of check passes than it used to.

`watcher.py:743-745` bails the whole pass if any square is `?`. The fix is to skip `?` in
`_wrong_squares` and `_walk`, with a floor on how many unknowns are tolerable.

Things the issue does not say, that the work has to settle:

- `check()` at :751 does `rows == grid_of(...)` for "position confirmed", and
  `_earlier_match` at :883/:886 does the same equality for takebacks. Both need a
  deliberate decision about `?`. "Position confirmed" while three squares are unknown is a
  judgement call.
- The pruning bound at :842 and :872 is `wrong > SQUARES_PER_MOVE * limit`. Skipping
  unknowns makes `wrong` smaller, which **loosens** the bound and lets more branches
  through. This runs live inside a 120 ms frame, so it has to be timed at depth 4 with the
  maximum tolerated unknowns.
- `board_from_grid` should keep refusing `?`. A cold start needs every square.

**The thing that must be measured, not assumed:** wildcards make ties more common, and
`_solve` returns `None` when more than one sequence fits. So the "caught up N missed moves"
path will fire *less* often. A fix that unblocks the check pass but then refuses every time
is worth nothing. Measure catch-up rate before and after.

**The dangerous interaction nobody has checked**, and it is not in the issue: this repo's
whole safety argument is "a frame that matches no legal successor is ignored, which rejects
animation, dragged pieces and dialogs for free". Wildcards weaken exactly that rejection.
A board mid-animation already reads as a legal move that never happened (documented: `e3`
during `e2-e4` holds ~86 ms). With squares also unknown, the wildcard search may accept a
phantom move that `main` would have rejected. Build that case with `fakeboard.Renderer` by
compositing a piece part-way between two squares, and check it.

**Zero false positives is the gate.** A check pass that records a move that did not happen
is strictly worse than one that refuses.

### #9 Show the best move for both sides -- WIP, pushed, DO NOT MERGE

Branch: [`coach-both-sides`](https://github.com/EnesYilmazcode/ChessOverlay/tree/coach-both-sides), commit `1c87f69`, marked WIP.

Touches `chesswatch.py`, `overlay.py`, `overlaytest.py` and both READMEs.

Done and worth keeping: the second arrow colour is **violet `#A64BFF`**, greyed value 118,
chosen over orange `#FF9800` and blue `#605DFF` by a judge that re-ran the measurements
itself.

- Orange was disqualified: composited, it sits **3.9 dE** from chess.com's yellow last-move
  highlight under deuteranopia, and 7.7 under protanopia, against a JND of about 2.3. That
  is not an exotic backdrop. The last move is highlighted every move, and the opponent
  arrow this feature adds very often starts or ends on exactly those squares, because the
  coach is answering the position that highlight just created. The new half of the feature
  would vanish where it is most wanted.
- Blue collapses to **17.3 dE** from cyan under tritanopia, since both are blues. Violet
  holds 20.1 worst case across normal, protan, deutan and tritan.
- Violet's one soft number, stated rather than hidden: 10.1 dE against the red check marker
  under tritanopia. The cyan arrow that already ships sits at 13.1 dE against a plain dark
  square under the same simulation, so it is not a new class of problem.

The safety property turned out to be **binary, not graded**: because `PIXEL_TAG` maps every
in-band grey to 0, the composite always lies between the background luma and the arrow
luma, so an arrow can only ever *remove* pixels from a count, never add one. Verified
exhaustively over 256 backgrounds x 256 coverages x 8 alphas, and again under both sRGB and
linear-light blending. Zero band exits.

## How the work was being run

Each issue got a Workflow with roughly this shape, and it earned its keep every time:

```
Measure (establish the baseline by running main)
  -> Design    (2-3 independent approaches, each measured)
  -> Judge     (picks one AND re-runs the top two itself, because
                design agents overstate their own numbers)
  -> Implement (into a git worktree, never the live checkout)
  -> Verify    (4 adversarial lenses, each told to BREAK it)
```

The judge re-running things caught real errors twice. The verify lenses caught the README
check-count drift on #13 and the whole dead-API problem on #12.
